# Domain rules

Full detail, file paths, and line numbers: `docs/discovery/DOMAIN_MODEL.md`. This is the condensed version for reasoning about correctness.

## Barefoot Investor accounts (the core allocation rule)

Every transaction posted to the virtual `Income` account is split across four buckets by a per-user ratio (default 60/10/10/20, must sum to 100%):

| Account | Default % | Purpose                                      |
| ------- | --------- | -------------------------------------------- |
| Daily   | 60        | Everyday spending                            |
| Splurge | 10        | Guilt-free discretionary spending            |
| Smile   | 10        | Medium-term savings goals ("Smile Projects") |
| Fire    | 20        | Emergency fund ("Fire Emergencies")          |

**The entire mechanism is one function**: `AppStateService.getAmount(account, ratio)` — for a transaction posted directly to `account`, add its amount; for a transaction posted to `Income`, add `round(amount * ratio, 2)`. There is no automatic overflow-forwarding between buckets (e.g. a full Fire bucket does not automatically spill into Mojo) — don't assume Barefoot's book describes exactly what this code does; the code is the source of truth.

**Mojo** is a separate singleton (`{target, amount}`), conceptually the long-term reserve nested under Fire, sized in "months of expenses covered." A transaction tagged `@Mojo` routes there directly, bypassing the daily/splurge/smile/fire split. Mojo is capped at its `target` — never allowed to exceed it (this cap is implemented three times in slightly different places; see `DOMAIN_MODEL.md` §4 item 6 before adding a fourth copy).

## Rich Dad Poor Dad / Grow

The RDPD "cash-flow quadrant" concept named in earlier planning docs was **never implemented and is out of scope** — don't build it. What exists is the **Grow** feature: asset-vs-liability tracking with buy/sell/dividend/payback/cashflow actions and a profit/loss figure labeled "GV" (German _Gewinn/Verlust_).

- A Grow project embeds a **denormalized copy** of its underlying `Share`/`Investment`/`Liability` at creation time. The real, balance-affecting records live in separate top-level arrays (`allShares`, `allInvestments`, `liabilities`), linked to the Grow project only by matching `tag === title` strings. These two representations can drift — a renamed Grow project silently breaks the link. When building the API's typed Grow actions (`docs/adr/0003-api-ui-write-consistency.md`, D-16), keep both representations in sync explicitly; don't just update one.
- **Never generate or hand-parse the `Transaction.comment` DSL** (`"Buy Share X 10 x 25;"`). It's a fragile, unvalidated mini-syntax that the API replaces with explicit typed actions. If you need to understand what it means, see `DOMAIN_MODEL.md` §2 "Greenfoot Investor calculations" — but write new code against the typed actions, not the string format.
- Asset vs. liability classification: `Grow.isAsset: boolean`. **The real balance sheet (`computeBalanceSheet()` in `statement-calculations.ts`) does not consult this flag at all** — it sums the separate top-level arrays directly. Don't assume `isAsset` drives the balance sheet; it doesn't.

## Custom concepts

- **Smile Projects / Fire Emergencies**: near-identical shape — a project has one or more **buckets** (sub-goals, each with its own `target`/`amount`), links, action items, and notes, moving through phases `idea → planning → saving → ready → completed`. The project's own total is never stored — it's always derived by summing buckets, and that sum is recomputed independently in many places (Smile has no shared helper at all; Fire has a partially-shared one). If you're building an API read endpoint for a project total, use one canonical calculation and reference it from `docs/domain/`, don't add a tenth ad hoc `reduce()`.
- **Subscriptions**: recurring transactions, one of 5 frequencies (weekly/biweekly/monthly/quarterly/yearly), generated by a clean Strategy-pattern implementation (`frequency-strategies/`) — this is the best-tested part of the domain layer and a good model to imitate for new calculators. `PlannedSubscription` is a separate, richer type used to auto-fund Smile/Fire buckets — don't confuse it with a regular `Subscription`.
- **Budget**: plan-vs-actual per category per month. No dedicated service exists today; logic lives directly in `plan.component.ts`.
- **`@` category prefix**: marks a transaction's `category` as a reference to a named entity (a revenue tag, a Smile/Fire project or bucket title, a Grow project title, a liability tag). Matching is case-insensitive string equality after stripping `@` — there is no real foreign key anywhere in this data model. Any new entity-linking mechanism you design for the API should use real IDs, not perpetuate this convention.
- **`#bucket:Name:Amount` comment tag**: records how a transaction's amount was split across a project's buckets. Parsed by `IncomeStatementService.parseTransactionBucketAllocations`.

## Known-disagreeing calculations — don't silently pick one

Two independently-computed "Savings Rate" values exist (`stats-calculations.ts` for the KPI dashboard, `statement-calculations.ts` for the Financial Statement page) and can legitimately produce different numbers for the same period, because they use different income aggregation and transfer-exclusion rules. Per `PLAN.md` D-7, the API exposes **both**, distinctly named (`financialStatement.savingsRate`, `kpi.savingsRate`), each documented with its exact formula. Do not merge them into one "correct" value without a product decision from JFK.

## Money representation

Today: decimal float everywhere in the frontend (`amount: number`). New domain-package/API code: integer minor units + ISO-4217 currency code, per `docs/adr/0002-money-minor-units-migration.md`. A document's `meta/schemaVersion` field tells you which representation that user's stored data is in — always check it before doing arithmetic on a raw value read from storage.
