Pro API & Connecting an AI Assistant

Self-hosted only. Your instance exposes a full REST API and an MCP server so an AI assistant like Claude can read and manage your finances directly, on your own server, under your own access token.

What this is

The Pro API (/api/v1) is a versioned REST API alongside the app's normal backend — everything the UI can do (transactions, Smile/Fire/Mojo, Grow, budget, reports, and more) is also available as an HTTP API, authenticated with a personal access token (PAT) instead of your login session. On top of that, apps/mcp in the project repo wraps the same API as an MCP server, so tools like Claude Code and Claude Desktop can call it as native tools rather than raw HTTP requests.

This page covers the practical setup. Full technical reference — every endpoint, request/response shape, and scope — lives in docs/api/openapi.yaml and docs/api/MCP.md in your deployment's repo checkout.

1. Mint a personal access token

A PAT is scoped and revocable independently of your login — it never expires unless you set expiresInDays, and you can revoke it any time without changing your password. There's no in-app screen for this yet, so it's a one-time API call using your existing session: 

curl -c cookies.txt -X POST https://YOUR-DOMAIN/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"YOUR_PASSWORD"}'

curl -b cookies.txt -X POST https://YOUR-DOMAIN/api/v1/auth/tokens \
  -H "Content-Type: application/json" \
  -d '{"name":"claude","scopes":["transactions:rw","reports:r"],"expiresInDays":90}'

The second call's response contains the token itself, under token — copy it now, it's shown exactly once and can't be retrieved again (you'd revoke and re-issue instead).

Picking scopes

Scopes are <resource>:<r|w|rw|bulk>, one per resource — there's no single "everything" scope. For an assistant that should handle normal day-to-day app usage (transactions, projects, budget, reports) but never touch account settings, your profile, or encryption config, use: 

transactions:rw,transactions:bulk,subscriptions:rw,subscriptions:bulk,
smile:rw,fire:rw,mojo:rw,grow:rw,balance:rw,budget:rw,income:r,reports:r

income and reports are read-only by design — there's no write endpoint for either. data:bulk (full plaintext account export/import) is deliberately left out of that list — it's the single highest-blast-radius scope in the system, worth adding only if you actually want an assistant able to export or overwrite your entire account in one call. Never grant admin to a token meant for an assistant — the API refuses to issue it to a PAT at all.

2. Connect Claude Code or Claude Desktop (MCP)

The project repo ships a ready-to-use MCP server (apps/mcp) and a checked-in .mcp.json that reads its configuration from two environment variables — set these in the shell you launch Claude from: 

export MM_API_URL="https://YOUR-DOMAIN/api/v1"
export MM_API_TOKEN="<the PAT from step 1>"

Restart Claude Code (or reconnect the MCP server) from inside your repo checkout and it will pick up money-manager as an available MCP server automatically — no further configuration. For Claude Desktop, add the same command/args/env to its own MCP server config file (see Anthropic's current Claude Desktop docs for its exact location).

Once connected, call get_identity first — it returns exactly which scopes your token has, so the assistant (and you) can confirm what it's actually allowed to do before trying anything else.

3. Connect remotely with your login (recommended)

The self-hosted stack runs the MCP server as its own always-on service (mcp, alongside backend and frontend in docker-compose.yml/ k8s/), reachable at your same domain — docker-compose up or a normal deploy sets this up automatically, nothing extra to run. It supports full OAuth: point a remote MCP client (Claude Code/Desktop's remote-server config, or any other OAuth-capable MCP client) at: 

https://YOUR-DOMAIN/mcp

The client discovers everything else itself (this is standard OAuth 2.1 + dynamic client registration, not a custom scheme) and opens a login page in your browser — sign in with your normal Money Manager email/password, review the scopes being requested, and approve. That mints a PAT behind the scenes with exactly those scopes and hands it to the client — nothing to copy-paste, and no separate token to manage: revoking it later is the same DELETE /api/v1/auth/tokens/{tokenId} call as any other PAT (see "Keep in mind" below).

Set MM_MCP_PUBLIC_URL in your deployment's environment to your real public HTTPS domain before relying on this — it's baked into every URL the server advertises to clients, so a wrong value (e.g. left at the internal/local default) breaks discovery for everyone even though the server itself starts fine.

Advanced: a manually-minted token instead

Any client that isn't going through the OAuth dance — a script, a CI job, or an MCP client that only supports a plain bearer header — can skip the browser login entirely and use the PAT from step 1 directly against the same URL: 

Authorization: Bearer <the PAT from step 1>

Both paths end up in the same place: an Authorization: Bearer header carrying a PAT, checked the same way either way. Use whichever is more convenient for the client you're configuring.

Keep in mind

  • Treat a PAT like a password — anyone holding it can act as you within its scopes.
  • Revoke a token you no longer want active with DELETE /api/v1/auth/tokens/{tokenId} rather than just forgetting about it.
  • Any delete, or any :bulk-scoped action (batch/export/import/recalculate), requires the caller to explicitly pass confirm: true — both the MCP tools and the raw API refuse those calls otherwise.
