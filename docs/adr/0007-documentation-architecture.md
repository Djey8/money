# 0007. Documentation architecture — spec generation and sync

## Status

Accepted

## Context

Master prompt §4.5 requires deciding file locations, whether OpenAPI is generated from code or code from spec, and how docs stay in sync (the `api-doc-auditor` subagent plus a CI check). §6 (Phase 4) lists the concrete files: `openapi.yaml`, `README.md`, `AGENTS.md`, `ERRORS.md`, `llms.txt`, `docs/domain/`.

## Decision

**Spec-first: `docs/api/openapi.yaml` is hand-authored and is the source of truth; code is written to match it, not the reverse.** Rationale: this backend has no existing framework-level route/schema decorators to generate a spec from (`backend/routes/*.js` are plain Express handlers, `ARCHITECTURE.md` §5), so "generate spec from code" would mean adding an annotation layer with no other benefit; writing the contract first also matches `mm-add-api-endpoint`'s step 1 ("OpenAPI contract first, before any code") and keeps the human-reviewable artifact (the spec) as the thing that changes intentionally, rather than a generated byproduct that drifts silently.

- The backend serves the spec at `/api/v1/openapi.json` (converted from the checked-in YAML at build/start time — a small script, not a second hand-maintained copy) and renders it at `/api/docs` (a lightweight static viewer, e.g. Redoc or Swagger UI served as a static asset — decided at Phase 4 implementation time, not here).
- File locations (all under `docs/api/`, per master prompt §6): `openapi.yaml`, `README.md`, `AGENTS.md`, `ERRORS.md`. `llms.txt` at the docs root (repo root's `docs/`) pointing into `docs/api/`. `docs/domain/` holds the Barefoot/Grow/custom-concept explanations, linked from the API docs rather than re-explained there (per master prompt §6's explicit instruction).
- **Sync enforcement**: the `api-doc-auditor` subagent (already defined in Phase 1, `.claude/agents/api-doc-auditor.md`) runs the checks described there. A CI job (`docs-sync`, added when Phase 4 implementation lands) runs an equivalent script-based check — every route in `backend/routes/*.js` has a matching `operationId` in the spec, every operation has an example and error section — and fails the build on drift, since a subagent alone (invoked on demand) isn't a hard CI gate.
- `mm-add-api-endpoint`'s step 5 (docs) and step 7 (verify/review) already bake "update the spec" into the per-slice workflow — this ADR just fixes spec-first as the direction so that workflow doesn't drift into code-first over time.

## Consequences

- Every new endpoint requires a spec edit before code — a small amount of upfront ceremony per endpoint, traded for a spec that's never stale by construction (enforced further by the CI sync check).
- No codegen toolchain (e.g. `tsoa`, `express-openapi-validator`'s route-generation mode) is introduced — request validation still uses a schema library (zod/valibot, decided per `mm-conventions`) written to match the spec by hand, which means validation schema and spec schema must be kept consistent manually; `api-doc-auditor` and the CI check are the mechanisms that catch drift here, not a shared-schema codegen step. If this manual consistency becomes a recurring source of bugs during Phase 3, revisit toward a shared-schema-generates-both approach as a follow-up ADR.
- The MCP server's tool schemas (ADR-0008) are derived from this same spec, so the spec-first decision here is also what makes "MCP tool schema derived from OpenAPI, not hand-duplicated" (master prompt §7) practical.
