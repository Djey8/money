# 0008. MCP server design

## Status

Accepted — implemented in Slice 7 (Phase 5). One deliberate deviation from this ADR's original wording, noted in Consequences: the "explain" tools shipped as a single `explain_concept` tool with a `topic` argument, not one tool per concept. The Streamable HTTP transport described as deferred below was added later (2026-09-13) — see "HTTP transport, implemented" in Consequences.

## Context

Master prompt §4.6/§7 requires deciding: generated from OpenAPI vs. hand-written, transport (stdio for Claude Code/Desktop, streamable HTTP for remote use), and how tokens are supplied (env var/config, never in prompts). `RISKS_AND_QUESTIONS.md` C-3/D-6 already decided the MCP layer does not need to implement the `todo/ai.md` anonymization principle, since a self-hosted PAT is treated as sufficient consent.

## Decision

- **Package**: `apps/mcp`, a new npm workspace member (extends the workspace introduced in ADR-0005), TypeScript, one MCP tool per operation group (not one tool per raw HTTP endpoint — e.g. a single `manage_transactions` tool with an `action` parameter covering list/create/update/delete/copy reads more naturally to an LLM than five near-identical tools, mirroring how `docs/api/AGENTS.md`'s task-oriented framing works). Read-only "explain" tools for domain concepts (e.g. `explain_barefoot_allocation`, `explain_grow_pnl`) are backed by `docs/domain/` content, loaded at startup, not re-fetched per call.
- **Schema generation**: tool input schemas are derived from `docs/api/openapi.yaml` (ADR-0007) at build time by a small generator script — not hand-duplicated, and not regenerated from route code directly (there is no route-code generation source per ADR-0007's decision). Tool descriptions (the free-text "when to use this, what it returns, side effects" per master prompt §5.1) are hand-written, not derived, since a good LLM-facing description requires judgment a generator can't produce from a schema alone.
- **Transport**: stdio as the primary, default transport (Claude Code, Claude Desktop) — matches the master prompt's explicit preference and needs no additional infrastructure. Streamable HTTP is added as a second transport for remote/multi-user use (e.g. claude.ai connectors) once local stdio use is validated in the Phase 5 smoke test — not built speculatively ahead of that validation.
- **Token supply**: `MM_API_URL` and `MM_API_TOKEN` environment variables only. The server never accepts a token as a tool argument, never logs it, and never echoes it back in a tool result — matching the encryption-key handling rule in ADR-0001/`PLAN.md` D-5 (same rationale: nothing capable of ending up in a transcript or prompt).
- **Destructive tools**: any tool whose underlying endpoint requires the `:bulk` scope, or is a delete, requires an explicit `confirm: true` argument, and its description states this plainly, per master prompt §7. This is enforced twice — once by the tool declining to act without `confirm: true`, and again by the underlying API endpoint's own scope/idempotency requirements (ADR-0006) — so a bug in one layer doesn't remove the safeguard entirely.
- **`.mcp.json`**: provided at the project root for Claude Code (project scope), documented setup snippet for Claude Desktop, verified at implementation time against the current Claude Code MCP docs (`code.claude.com/docs/en/mcp.md`) rather than assumed from this ADR, since MCP configuration conventions can change between when this is written and when Phase 5 is implemented.

## Consequences

- The MCP layer has a hard dependency on the OpenAPI spec (ADR-0007) being accurate and current — another reason the spec-sync CI check matters, since MCP tool generation would otherwise silently drift too.
- Grouping tools by operation rather than 1:1 with endpoints means the MCP layer has its own thin dispatch logic (mapping a tool call + action to the right HTTP call) — a small amount of code that has no OpenAPI-spec equivalent and needs its own tests.
- If MCP's stdio smoke test (master prompt §7, `docs/api/MCP.md`) surfaces that Money Manager isn't a good fit for MCP for some reason discovered during implementation, the master prompt's own fallback applies: document the plain-HTTP workflow for a Claude chat instead — this ADR doesn't foreclose that, it just states MCP is the first thing attempted, per instruction.
- **Naming correction from implementation**: this ADR's Decision section named `explain_barefoot_allocation`/`explain_grow_pnl` as illustrative examples of per-concept explain tools. The shipped implementation (`apps/mcp/src/tools/explain.ts`) instead exposes one `explain_concept` tool with a `topic` enum, auto-discovered from `docs/domain/*.md` at startup — functionally equivalent (still loaded once at startup, still backed by the same docs) but scales to new `docs/domain/` files without a matching MCP code change, unlike a fixed one-tool-per-concept list. Recorded here so a future reader doesn't go looking for tools literally named `explain_barefoot_allocation`.
- **HTTP transport, implemented (2026-09-13)**: `apps/mcp/src/http-server.ts` adds the Streamable HTTP transport this ADR deferred, using the SDK's `StreamableHTTPServerTransport`/`createMcpExpressApp`, selected via `MM_MCP_TRANSPORT=http` (default remains `stdio`; `index.ts` picks between them). Key decisions made during implementation, not fully specified above:
  - **Auth model when this was first shipped was plain bearer PAT reuse, not OAuth** — superseded the same day, see "OAuth, implemented" below. Every other client of the self-hosted API authenticates the same way (ADR-0006's PATs, `Authorization: Bearer <token>`), and this transport did not introduce a second auth system: each `initialize` request had to carry the caller's own PAT as a bearer header, and the MCP session created from that request was permanently bound to an `ApiClient` built with that exact token (`buildServer({ apiUrl, apiToken })` — the same `buildServer` the stdio path already used, now called once per HTTP session instead of once per process). No token was ever read from an environment variable in HTTP mode; `MM_API_TOKEN` stayed stdio-only, matching `loadHttpConfig`'s split from `loadConfig` in `config.ts`.
  - **Session model**: stateful, in-memory, one `StreamableHTTPServerTransport` (and its own `Server`/`ApiClient`) per `mcp-session-id`, generated via `randomUUID()` on a successful authenticated `initialize`. A request carrying an unrecognized session ID is rejected (404), not silently treated as a fresh session — a stale/guessed session ID must never establish a session without ever presenting a bearer token. Sessions live only in the process's memory (no `EventStore`/resumability, no persistence across a restart) — acceptable for a personal, single/few-user deployment; would need revisiting for multi-replica or resumable-stream requirements.
  - **Deployment/exposure**: wired into `docker-compose.yml`/`k8s/mcp.yaml` the same day OAuth was added — see "OAuth, implemented" below for that half of the story.

- **OAuth, implemented (2026-09-13, same day as the HTTP transport above)**: adds a real OAuth 2.1 authorization server + resource server to the HTTP transport, so a user can connect Claude by logging in through a browser rather than hand-curling a PAT. Built using the SDK's `mcpAuthRouter`/`requireBearerAuth` (`apps/mcp/src/oauth/`), not hand-written RFC-compliance code.
  - **This is not a general-purpose OAuth AS — it's the existing login/PAT system wearing an OAuth-shaped front door.** `MoneyManagerOAuthProvider.authorize()` (`apps/mcp/src/oauth/provider.ts`) redirects the browser to a small login+consent page this server renders itself (`apps/mcp/src/oauth/login-page.ts`); submitting it calls the _existing_ `POST /api/auth/login` (`backend-client.ts`'s `loginWithPassword`) and then the _existing_ session-authenticated `POST /auth/tokens` (`mintPersonalAccessToken`) to mint a real PAT scoped to whatever was requested (`admin` always stripped, falling back to the "everything except settings" bundle in `DEFAULT_SCOPES` when the client asked for nothing specific). The OAuth "access token" handed back from the token endpoint _is_ that PAT, verbatim — `verifyAccessToken` on the resource-server side is just `GET /me` (the same identity check `get_identity` already used). No new token type, no new storage, no new revocation path: revoking the PAT via the existing `DELETE /auth/tokens/:id` (or the UI, once one exists) revokes OAuth-issued access exactly the same as a hand-curled one. This reuses 100% of ADR-0006's scope/revocation model rather than building a second auth system alongside it, which the original HTTP-transport bullet above had assumed would be the tradeoff for skipping OAuth — turned out not to be a real tradeoff once "authorize" was reframed as "log in and mint a PAT" instead of "build a token store."
  - **No refresh tokens, no dynamic-client persistence.** `exchangeRefreshToken` always throws `UnsupportedGrantTypeError` — a PAT doesn't expire on an OAuth-style schedule, so there's nothing to refresh. Registered OAuth clients and in-flight authorize requests live only in the process's memory (`InMemoryClientsStore`, a `Map` of pending requests/codes with TTL-based pruning) — a restart means any client must re-register (transparent to the user; MCP clients re-run DCR automatically) and any in-flight login must restart. Acceptable for a personal, low-traffic deployment.
  - **Routing gotcha, found by testing against a real proxy, not by inspection**: `mcpAuthRouter` mounts `/authorize`, `/token`, and `/register` at the **app root**, not under an `/oauth/` prefix — only this app's own login page (`/oauth/login`) uses that prefix. `nginx.conf`'s reverse-proxy rules were originally written proxying only `/oauth` and missed the root-level paths entirely (silently falling through to the frontend's static-file catch-all, returning a misleading 405 instead of reaching the MCP server at all). Caught by actually driving the full DCR+authorize+login+token dance through a running nginx container on the real `docker-compose` network, not by reading the SDK's source — confirmed by fetching `.well-known/oauth-authorization-server` from the live server and checking its advertised endpoint URLs match what nginx actually routes. `nginx.conf` now has an explicit `location ~ ^/(authorize|token|register)$` block alongside `/oauth`, `/mcp`, and the two `.well-known/oauth-*` paths, all proxied to the `mcp` service — the same single-domain-proxy pattern already used for `/api` → `backend`.
  - **`MM_MCP_PUBLIC_URL` is now load-bearing, not cosmetic.** It's the OAuth issuer and the base every metadata document/redirect URL is built from (`loadHttpConfig` in `config.ts`) — get it wrong (e.g. leave it pointing at an internal `http://mcp:3939` instead of the real public domain) and every client's discovery step resolves to an address it can't reach, while the server itself starts and looks healthy. `k8s/mcp.yaml`'s ConfigMap hardcodes it to the production domain (matching the existing `CORS_ORIGINS` pattern in `backend-config`); `docker-compose.yml`/`.env.example` default it to `http://localhost:3939` for local testing only.
  - **Verified end-to-end against a real backend + CouchDB, twice**: once via `apps/mcp/tests/integration/oauth-smoke.test.ts` (mirrors the existing stdio `smoke.test.ts` — real account registration, real bcrypt login, real minted PAT, real `/mcp` tool call, no mocks), and once by hand — full `docker-compose up` with `couchdb`+`backend`+`mcp`+`frontend`, driving the entire DCR→authorize→login→token-exchange→`/mcp` dance with `curl` through the real nginx proxy on port 80, confirming the minted token shows up as a real row in the account's PAT list. `apps/mcp/tests/unit/oauth-provider.test.ts`, `backend-client.test.ts`, and the OAuth-flow cases in `http-server.test.ts` cover the same logic with `backend-client` mocked, for fast iteration.
  - **claude.ai web/mobile support is more plausible now, still not confirmed against the live product.** The server now implements the actual mechanism the MCP authorization spec expects (OAuth 2.1, PKCE, dynamic client registration, RFC 9728 protected-resource metadata with a `WWW-Authenticate`/`resource_metadata` discovery hint on 401) rather than a bespoke bearer scheme — this is what a spec-compliant remote MCP client is supposed to be able to discover and drive unassisted. Whether claude.ai's own connector UI actually completes that flow against a small, non-well-known self-hosted server was not tested here and shouldn't be assumed either way until checked. Confirmed working: any client that can be pointed at an OAuth-capable MCP server URL (Claude Code/Desktop's remote-server config, in particular, and the manual bearer-PAT path both still work unchanged).
  - **`scripts/deploy.sh`/`scripts/deploy-local.ps1`** got a mirrored `--skip-mcp`/`-SkipMcp` build-and-deploy path (image build, K3s import, `kubectl apply -f k8s/mcp.yaml`, rollout restart, readiness wait) following the exact structure already used for backend/frontend — syntax-checked (`bash -n`, PowerShell AST parse) but **not run against a live K3s cluster from this environment**; the docker-compose path was the one actually exercised end-to-end above. Worth a real dry run on the target Pi before depending on it blind.
