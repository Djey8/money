# Subscriptions: use cases, what was wrong, what is fixed

Walked through as a user (JFK, 2026-10-10): _"update the end date of a subscription I finished - it says updated, I refresh,
nothing saved"_, _"changing details should replace the old transactions, an earlier end date should remove the later ones, a
later one should add the missing ones"_, _"the cashflow sums and the budget fill ignore monthly / weekly / yearly"_.

A subscription has no link to the transactions it generated. They are recognised by what they look like (account, amount,
category, comment `title` or `title + comment`, possibly followed by `#bucket:` tags) **and** a date that was one of the
subscription's occurrences - `packages/domain/src/transactions/subscription-sync.ts`. One rule covers every edit: _change what the old subscription generated in place where the new one still has an occurrence for it (same id, same
place in the list), remove what it has none for, then generate what the new one is due and lacks (appended)._ Occurrences are paired by
period (same month / quarter / year; nearest day within half an interval for weekly and biweekly).

## Not reproduced

"Updated, but gone after a refresh" did **not** reproduce with a clean account (end date and amount edits were stored, also
with another write in between). What the review found that fits the symptom: row 9 (the message did not wait for the writes -
a stale-version refusal after an agent, the game or another tab had written meant "updated" on screen and nothing stored) and
row 10 (with a frequency filter on, the edit hit another subscription). If it happens again with a normal list, the browser
console shows the failing write (`[Write] Failed: ...`) and the error message now stays visible.

## Open

- The app still writes fourteen collections one by one for every subscription change (`updateStorage`); one batch write
  (`persistence.batchWriteAndSync`, as the add form does) would be faster and all-or-nothing.
- Row 14.
- The refresh creates each generated transaction with its own database write; a long gap (a subscription started years ago)
  makes many writes in a row.
