## Phase 0 — Discovery: summary

**Status: complete, approved by JFK (see Decisions log).**

Discovery docs are at `docs/discovery/`: `ARCHITECTURE.md`, `DOMAIN_MODEL.md`, `FEATURE_CATALOG.md`, `RISKS_AND_QUESTIONS.md`. Full detail lives there; this is the ≤1-page summary required by §2.5.

**What the repo actually is**: a single Angular 20 SPA (not a monorepo) with two independently-built, independently-deployed editions — Firebase (Firebase Auth + Realtime DB, auto-deployed on every conventional-commit push to `main`) and self-hosted (Express + CouchDB, deployed via Docker Compose or K3s). The two editions share code but **no data or sync mechanism** — the only bridge between them is a manual JSON export/import a user can trigger themselves. Tests are green (776 frontend + 69 backend unit tests, run live in this session) and CI already runs `npm audit`, Trivy container scanning, gitleaks secret scanning, and SBOM generation — this repo is materially more mature on the security/supply-chain side than a first glance suggests. No linter is configured anywhere, and E2E (Playwright) is wired up but disabled in CI.

**The central finding that reshapes Phase 2**: today's self-hosted "backend" is not a per-entity API — it's a generic per-user JSON-blob store addressed by string paths (`read/transactions`, `write/smile`, etc.), mirroring Firebase Realtime DB's own path model. Every entity's schema, validation, and business rules (Barefoot Investor account splitting, Grow buy/sell/P&L, Smile/Fire bucket goals, budget, statistics) live entirely client-side in Angular, several with real bugs and heavy duplication (see `RISKS_AND_QUESTIONS.md` R-5 and `DOMAIN_MODEL.md` §4). Building the Pro API therefore means writing genuine server-side entity models for the first time, not exposing something that already exists — this changes the Phase 2 effort estimate materially versus what the master prompt implicitly assumed.

**Other load-bearing findings**: client-side database encryption is user-toggleable and, when on, makes the backend blind to plaintext — this needs an explicit ADR reconciling it with the Pro API's filtering/sorting/audit requirements (R-2). Money is stored as floats everywhere, confirming the ISO-4217 minor-units migration is real, cross-cutting work, not a contingency (R-3). There's already a shipping, philosophically different "AI" feature (a client-side, anonymized-by-default copy-paste prompt generator) that the MCP/agent design needs to be reconciled with in the docs, not silently duplicated (R-4). "Greenfoot Investor" and RDPD "cash-flow quadrants," named in the master prompt as founding frameworks, do not appear anywhere in the codebase — the closest analogue is the `Grow` feature, but this mapping is unconfirmed (open question C-1).

**Recommendation**: proceed to Phase 1 (agent-readiness) in parallel with resolving the Phase 0 open questions in `RISKS_AND_QUESTIONS.md` §C, since none of them block writing `CLAUDE.md`/skills/subagents. Phase 2's architecture work should not start until at least questions C-1, C-2, C-4, and C-6 have an answer, since they change what the endpoint matrix and domain-package extraction actually cover.

**Open questions**: see `docs/discovery/RISKS_AND_QUESTIONS.md` §C (7 numbered questions, each with a concrete recommendation).

### API conventions (§4.2, not already covered by an ADR above)

- Base path `/api/v1`, JSON, UTF-8, ISO-8601 UTC timestamps, cursor pagination (`?cursor=`, `?limit=`) on every list endpoint, filtering/sorting query params documented per-endpoint in the spec.
- Optimistic concurrency: every update accepts `If-Match` (preferred) or a body `version` field, checked against the entity's stored `updatedAt`/revision; mismatch → `409` Problem Details.
- Errors: [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details (`type`, `title`, `status`, `detail`, plus a stable `code`). Error code categories to be enumerated in full in `docs/api/ERRORS.md` (Phase 4): `auth_*` (invalid/expired/revoked token), `scope_*` (missing/insufficient scope), `validation_*` (schema failures), `conflict_*` (optimistic concurrency, idempotency replay mismatch), `not_found_*`, `rate_limit_*`, `encryption_*` (missing/invalid key for a request that needs one).
- Idempotency: every `:bulk` endpoint requires an `Idempotency-Key` header; replaying the same key returns the original result without reapplying the write (test required per `mm-add-api-endpoint`).

**Deferred, not silently dropped: the Grow comment-DSL rewrite.** A closer read of `grow.component.ts` (generation) and `add.component.ts` (parsing — `info.component.ts`'s parallel edit-flow implementation not yet read) confirms this is bigger than the original estimate, not smaller. Twelve distinct formats confirmed so far, all parsed via `split(' ')` positional indexing with no validation:

1. `Buy Asset {title} 1 x {amount};`
2. `Sell Asset {title} 1 x {amount};`
3. `Buy Share {title} {quantity} x {price};`
4. `Sell Share {title} {quantity} x {price};`
5. `Dividende Share {title} {quantity} x {price};`
6. `Buy Investment {title} {deposit} {mortgage};`
7. `Payback Liabilitie {amount|N%} {credit|N%};` — the amount/credit fields can each independently be an absolute number **or a percentage of the current liability** (`split[2].includes('%')` branches to a different formula entirely)
8. `Sell Investment {title} {deposit} {mortgage};` — sometimes preceded by a concatenated `Payback Liabilitie ...; ` fragment that must be split off first (`clean_comment.split('; ')`) before parsing this one
9. `CASHFLOW {value}` and `CASHFLOW {value} - CREDIT {value}` (two shapes, from `cashflowProject`)
10. `CASHFLOW: {value};` — a **third, colon-based** CASHFLOW shape, unrelated to #9, appended during the Sell Investment flow (`add.component.ts:1085`) — the DSL is inconsistent even with itself
11. `Deposit {value};` (from `depositProject`)
12. `Liabilitie {loan} {credit}; ` — prefixed onto whatever comment already exists when adding a **new** liability (`add.component.ts:930-936`), distinct from `Payback Liabilitie` above despite the near-identical name

**Confirmed real, pre-existing, currently-shipping bug found while reading this**: nothing strips or validates spaces out of a Grow project's `title` before it's interpolated into these comment strings (`add-grow.component.ts` only `.trim()`s leading/trailing whitespace). Worth a note to JFK independent of the DSL rewrite, since it may warrant a standalone `fix:` once confirmed against real usage.

Rewriting this correctly needs: characterization tests against all 12 (likely more, once `info.component.ts` is read) exact current formats including the percentage-payback and multi-fragment-concatenation behavior, a regex-based parser design that captures title non-positionally (anchoring on the fixed suffix pattern, e.g. `/^Buy Share (.+) ([\d.]+) x ([\d.]+);?$/`, so multi-word titles work correctly — which also happens to fix the bug above as a side effect of the rewrite, not a separate change), and a decision on whether to preserve percentage-based payback as a typed action variant. This is its own focused multi-session effort, not a squeeze-in. Recommend tackling it as its own slice-0.5, before or alongside slice 4 (where the typed Grow actions that replace it get built) — see D-9's characterization-tests-first cycle.

**Not yet done, and required before any production use** (per JFK's explicit "nothing breaks, must be reversible" requirement and `CLAUDE.md`'s ask-before list): every test above runs against mocks — there is no live CouchDB in this development environment (confirmed: no Docker/Podman available, no local CouchDB running; JFK declined installing one via Homebrew for now). **Root-caused and fixed, not just worked around: the recurring integration-test timeout was a real production performance bug, not test infrastructure.** `EncryptionSession.encrypt()` (`packages/domain/src/crypto/cryptic.ts`) defaulted to a fresh random salt on every call unless the caller explicitly pinned one via `saltHex` — but every one of the 5 backend call sites (`transaction-repository.js`, `transaction-derived-state.js`, the `backfill-transaction-ids`/`migrate` CLI commands, the batch/import idempotency payload) calls `encrypt()` without ever pinning a salt. Since a fresh salt means a fresh PBKDF2 derivation (10,000 iterations, deliberately slow, by design), and every transaction write/read independently encrypts/decrypts every field of every transaction, this meant **any self-hosted user with database encryption enabled would see write/read latency scale linearly with their transaction count** — not a test artifact, a real bug any encrypted-database user would eventually hit. Measured directly: 210 field-encryptions (30 transactions × 7 fields, roughly what one test user had accumulated) took 17.7s with the bug, 109ms once the session's own salt is reused by default.
